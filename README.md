## 1. Business Overview

Sri Lanka Police requires a centralised, real-time platform for tracking registered tuk-tuks (three-wheelers). The system provides:

| Feature | Description |
|---|---|
| Live GPS tracking | Last-known position for every active vehicle |
| Historical movement logs | Time-window and vehicle-scoped history queries |
| Province & district filtering | Jurisdiction-scoped access per officer rank |
| Role-based access control | HQ Admin → Provincial Admin → Station Officer → Device |
| Secure authentication | JWT Bearer tokens, bcrypt password hashing |

## 4. Getting Started

### Prerequisites
- Node.js >= 18
- Free [MongoDB Atlas](https://www.mongodb.com/cloud/atlas) cluster

### 1. Clone and install

```bash
git clone https://github.com/<your-username>/tuk-tuk-tracker.git
cd tuk-tuk-tracker
npm install
```

### 2. Configure environment

```bash
cp .env.example .env
# Edit .env — set MONGODB_URI and JWT_SECRET
```

### 3. Seed the database

```bash
npm run seed
```

Seeds: 9 provinces, 25 districts, 27 police stations, 5 users, **200 tuk-tuks**, and approximately **100,000+ location pings** covering 1 week of history.

### 4. Start the server

```bash
npm run dev     # Development (nodemon auto-restart)
npm start       # Production
```

|---|---|
| `http://localhost:3000/health` | Health check |
| `http://localhost:3000/api/docs` | Swagger UI |

## 5. Authentication & Roles

All endpoints (except `/api/auth/login`) require a Bearer JWT token.

### Login

```bash
curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@police.lk","password":"Password@123"}'
```

Use the returned token as: `Authorization: Bearer <token>`

### Role Hierarchy

| Role | Scope | Permitted Actions |
|---|---|---|

| `provincial_admin` | Assigned province | Manage stations and vehicles in province |

### Response Headers on Every GET

| Header | Example Value | Purpose |
|---|---|---|
| `ETag` | `W/"d41d8cd98f00"` | Conditional GET revalidation |
| `Cache-Control` | `no-cache` | Forces revalidation each request |
| `Link` | `<url>; rel="next", ...` | RFC 5988 pagination navigation |
| `X-Total-Count` | `200` | Total matching records |
| `X-Total-Pages` | `10` | Total pages |
| `X-Current-Page` | `1` | Current page |

### HTTP Status Codes

| Code | Condition |
|---|---|
| 200 | Successful GET / PUT / PATCH |
| 201 | Resource created (POST) |
| 304 | Not Modified — ETag matched (conditional GET) |
| 400 | Bad request, invalid ObjectId |
| 401 | Missing or invalid/expired token |
| 403 | Valid token but insufficient role |
| 404 | Resource not found |
| 409 | Duplicate unique key (e.g. registration number) |
| 422 | Mongoose validation failure |
| 429 | Rate limit exceeded |
| 500 | Unexpected server error |

## 7. REST Design Decisions

### Conditional GET (ETag / If-None-Match)
Every `GET` response carries a weak `ETag` header generated from an MD5 hash of the response body. Clients that cache the response can send `If-None-Match: <etag>` on subsequent requests. If the data is unchanged the server returns `304 Not Modified` with no body, saving bandwidth. This is implemented as an Express middleware (`src/middleware/etag.js`) that wraps `res.json`.

### Pagination via RFC 5988 Link Headers
Paginated endpoints return standard HTTP `Link` headers (`rel="next"`, `rel="prev"`, `rel="first"`, `rel="last"`). This follows the GitHub API convention and means clients never need to construct pagination URLs themselves. Alongside `X-Total-Count`, `X-Total-Pages`, and `X-Current-Page` headers, consumers have complete pagination context from headers alone — the response body only contains the page data.

### Role-Scoped Database Queries
The `protect` middleware attaches `req.user` to every request. Controllers inspect `req.user.role` and automatically narrow MongoDB queries: a `provincial_admin` calling `GET /tuktuks` only sees vehicles in their province; a `station_officer` only sees their district. No manual query-parameter filtering is needed by the client.

### TTL Index on LocationPing
MongoDB's TTL index automatically purges pings older than 90 days. This prevents unbounded collection growth at scale (200 vehicles pinging every 5 minutes = ~52 million pings/year) without any application-level scheduled job.

### Aggregation Pipeline for Live View
`GET /locations/live` uses MongoDB's aggregation pipeline to efficiently return exactly one (the most recent) ping per vehicle across the entire fleet in a single database round-trip, rather than N+1 queries.

### Three-Tier Rate Limiting
- **Global** (all routes): 200 req / 15 min — general abuse prevention
- **Auth** (`/login`, `/register`): 20 req / 15 min — brute-force mitigation
- **Ping** (`/locations/ping`): 1000 req / 15 min — allows high-frequency device updates

### Postman Collection

Import `TukTuk-Tracker.postman_collection.json` into Postman:
1. Set collection variable `baseUrl` to your API URL
2. Run **Auth > Login (HQ Admin)** — token is auto-saved to `{{token}}`
3. All other requests use `{{token}}` automatically

## 10. Deployment on Render.com

### One-time setup

1. Push code to GitHub and add your lecturer as a collaborator
2. Sign up at [render.com](https://render.com) (free)
3. **New Web Service** → connect your GitHub repo
4. Render auto-detects `render.yaml`
5. In the Render dashboard **Environment** tab, add:
   - `MONGODB_URI` — your Atlas connection string
   - `API_URL` — your Render URL (e.g. `https://tuk-tuk-tracker.onrender.com`)
6. Click **Deploy**
7. After deploy completes, open the **Shell** tab and run: `npm run seed`

### Useful URLs after deployment

| Purpose | URL |
|---|---|
| API base | `https://<app>.onrender.com` |
| Swagger docs | `https://<app>.onrender.com/api/docs` |
| Health check | `https://<app>.onrender.com/health` |

> Render free-tier services spin down after 15 min of inactivity. First request after a cold start takes ~30 seconds. This is fine for a coursework demo.
